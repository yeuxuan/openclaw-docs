# 重启恢复

Gateway 重启后，大家最关心的通常不是“进程有没有起来”，而是：

- 正在跑的任务会怎样
- 之前的会话会不会丢
- 聊天入口会不会恢复
- 有没有需要人工补救的地方

这一页就是回答这些问题。

---

## 先讲结论

重启恢复的重点不是“保证所有事情像没发生过一样继续跑”，而是：

- 让系统尽量回到可用状态
- 避免状态混乱或重复处理
- 明确哪些事情需要人工确认

所以你看到 Gateway 重启成功，不代表所有未完成任务都自动完美续上。

---

## 实际排查时先看什么

重启后如果你怀疑系统没恢复好，先按这个顺序查：

1. `openclaw gateway status`
2. `openclaw doctor`
3. `openclaw logs --follow`
4. 关键通道状态，例如 `openclaw channels status --probe`
5. 对应会话或 Agent 是否还能正常继续

这比先猜“是不是数据库坏了”“是不是插件没加载”更有效。

---

## 哪些东西通常能恢复

一般来说，下面这些更偏“应该恢复到可用状态”的范围：

- Gateway 主进程重新启动
- 控制 UI 恢复可访问
- 通道重新连上
- 已持久化的会话和状态重新可见

但“重新可见”不等于“每个正在执行的动作都自动接着跑完”。

---

## 哪些东西要特别小心

### 未完成的长任务

如果某个 Agent 任务在重启前正跑到一半，重启后要确认它是：

- 被安全终止
- 可以人工重试
- 还是已经留下半成品状态

不要想当然地认为它必然完整恢复。

### 外部系统副作用

如果任务在重启前已经对外部系统做了一半动作，比如：

- 发了一半消息
- 改了一半文件
- 调了一半第三方 API

恢复后要格外注意是否会重复执行。

### 通道侧重新投递

某些聊天平台在重连后可能会出现补投、重试或时序变化。
排障时要把“通道重试”和“OpenClaw 重复处理”区分开。

---

## 最稳妥的恢复心态

可以把重启恢复理解成：

```text
先恢复服务能力，再确认业务动作状态，最后决定是否人工补跑。
```

不要把它理解成“任何未完成任务都无缝继续”。

---

## 什么时候要把恢复问题当成正式故障

以下情况就不只是“重启了一下”：

- Gateway 能起来，但关键会话状态明显异常
- 重启后通道持续断连
- 任务重复执行，造成外部副作用
- 日志里不断出现恢复相关错误

这时就该结合日志、审计和对应会话一起查，而不是只盯 `gateway status`。
